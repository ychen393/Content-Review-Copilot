REFERENCE WORKFLOW
Project: Multimodal Content QA & Optimization Agent
Source basis:
1) Catcat draft / Coze workflow export
2) Workflow screenshots supplied by the user

Purpose:
This document is a sanitized functional reference for rebuilding the original Coze workflow as a standalone Python application.
It preserves the BUSINESS LOGIC, stage dependencies, branch behavior, input/output contracts, and key evaluation/generation rules.
It intentionally removes internal credentials, app tokens, table IDs, private URLs, customer records, and proprietary database identifiers.

======================================================================
0. ORIGINAL BUSINESS USE CASE
======================================================================

The original workflow is a social-media content diagnosis + rewrite system for Xiaohongshu-style branded content.

Core idea:

User supplies:
- content direction metadata
- keyword
- original text
- optional images

System then:
- normalizes business direction fields
- retrieves direction rules, sub-directions, keyword rules, RTB references, issue checklists and compliance rules
- performs image understanding
- applies hard deterministic compliance cleaning
- parses the content into title / opening / RTB / ending / tags
- predicts a persona
- runs parallel soft diagnosis on opening / RTB / ending
- retrieves persona DNA/style guidance
- builds a rewrite plan
- chooses one of two generation routes
- generates optimized content
- performs final deterministic review / assembly
- returns final text + report + preserved nouns
- in one branch, generated content is also persisted back to a data store

The rebuilt project should preserve this logic while replacing internal Feishu/Coze dependencies with local repository data providers.

6. PHASE D — HARD DETERMINISTIC RULE ENGINE
======================================================================

Original node:
N21 硬性问题判断+解决

Input:
- original_text
- compliance rule rows

Output:
- cleaned_text
- replacement_log

The original logic is NOT a naive global replace.

Important behavior:

1. Split banned terms on:
   - comma
   - Chinese comma
   - enumeration comma

2. Replace-list entries preserve empty values.
   Empty replacement means DELETE.

3. Mapping is positional:
   banned_words[i] -> replace_words[i]
   if replacement does not exist -> delete

4. Process longer banned phrases before shorter phrases.

5. Context-aware replacement:
   If a short banned term appears inside a longer allowed/compliant phrase,
   do not replace that occurrence.

6. If banned_word == replacement_word:
   skip the replacement.

7. Record:
{
  "banned_word": "...",
  "replace_word": "...",
  "count": n
}

This deterministic layer should remain separate from semantic LLM diagnosis.

Standalone module:
DeterministicRuleEngine

8. PHASE F — CONTENT PARSING + PERSONA MATCHING
======================================================================

Original node:
N16 文本拆分+匹配人设

Input:

Output:

{
  "title": "...",
  "opening": "...",
  "rtb_content": "...",
  "ending": "...",
  "tag": "...",
  "persona_name": "..."
}

Content splitting rules:

title:
- only return a title if clearly identifiable
- otherwise empty string
- do not manufacture a title from body text

opening:
- content before the RTB section
- usually scene setup / pain-point / transition

rtb_content:
- primary product proof / ingredient / benefit / certification section
- core persuasive section

ending:
- content after RTB
- summary / CTA / emotional close

tag:
- trailing hashtag area
- otherwise empty string

General rules:
- preserve source wording
- only segment; do not rewrite at this phase
- prioritize finding RTB boundaries first
- split on semantic boundaries, not mid-sentence
- missing sections -> empty string

Persona matching:
Select exactly one known persona from configured persona list.
Match based on:
- narrator identity
- parenting/user stage
- expertise level
- tone
- scene type
- recommendation style

19. IMPORTANT ARCHITECTURAL PRINCIPLES TO PRESERVE
======================================================================

1. Deterministic vs semantic separation
   Hard rules should not be delegated entirely to an LLM.

2. Retrieval before diagnosis/generation
   Business rules are retrieved from structured data sources.

3. Multimodal evidence
   Images are first converted into structured evidence, then consumed by evaluators.

4. Parallel diagnosis
   Opening / RTB / ending are evaluated independently.

5. Planning before rewriting
   Diagnosis outputs are aggregated into explicit rewrite plans.

6. Conditional generation
   Some content types use full rewrite; others use staged generation.

7. Sequential continuity
   In staged generation:
   opening -> RTB -> ending
   later stages receive earlier generated content.

8. Final independent review
   Generated text must be checked again before returning.

9. Structured outputs
   LLM nodes should return structured JSON/Pydantic-compatible responses.

10. Traceability
   Rebuilt system should record step-level execution trace.
